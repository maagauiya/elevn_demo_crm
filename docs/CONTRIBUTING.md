# Как устроен код и как в него добавлять

## Структура

```
src/
├─ app/          # точка входа, провайдеры, router, AppShell, сборка моков — общее, ревью обоих
├─ shared/       # не знает о фичах — общее, ревью обоих
│  ├─ ui/        # компоненты (shadcn/Radix + продуктовые примитивы), формы
│  ├─ styles/    # tokens.css — токены из design-system.md
│  ├─ api/       # callApi, ApiError, queryClient, контекст сессии
│  ├─ mocks/     # реестр MSW-моков, faker
│  ├─ i18n/      # i18next, общий неймспейс common
│  └─ lib/       # cn, статусы записей, телефон, даты, storage
└─ features/<name>/
   ├─ api/       # zod-схемы + query/mutation-хуки
   ├─ mocks/     # моки методов этой фичи
   ├─ components/
   ├─ pages/     # страницы роутов (грузятся лениво)
   ├─ locales/   # ru.json, en.json — неймспейс фичи
   ├─ i18n.ts    # регистрация неймспейса
   ├─ routes.tsx # роуты фичи (движки: /info/:itemId, /chart/:itemId, /dashboard/:itemId, /kanban/:itemId)
   └─ index.ts   # публичный API фичи
```

Границы проверяет ESLint:

- фича импортирует `shared/*` и **только `index.ts`** другой фичи (`@/features/auth`, не `@/features/auth/model/...`);
- `shared/*` не импортирует `features/*` и `app/*`;
- `app/` может всё (он собирает приложение).

`app/router.tsx` и `app/mocks/handlers.ts` уже подключают все фичи — их не нужно трогать
при работе над экраном.

## Добавить метод API + мок

1. В `features/<name>/api/` опиши zod-схему **одной строки** ответа в формате старого API
   (UPPERCASE, всё строками) и сразу преобразуй её в удобный вид через `.transform`.
   Для типичных полей есть `apiField.int`, `apiField.bool`, `apiField.optionalString`.
2. Вызывай через `callApi('MethodName', params, { schema, signal })` внутри `useQuery`/`useMutation`.
   Ключи запросов: `[feature, entity, params]`.
3. В `features/<name>/mocks/index.ts` добавь хендлер с тем же `MethodName`:
   получает тело запроса, возвращает массив строк. Бизнес-ошибка — `throw new MockError('текст', code)`.
   Данные — только синтетические: `createFaker(seed)` из `@/shared/mocks`.
4. Контракт метода смотри в базе: `pnpm api:describe <Метод>` (см. «Локальный бэкенд — правила»).
   Имена методов и параметров не меняй.

Пример — `features/auth/api/` и `features/auth/mocks/`.

`pnpm dev` ходит в локальный бэкенд, `pnpm dev:mocks` — в MSW. Мок нужен каждому методу, который
вызывается в тестах и e2e.

## Локальный бэкенд — правила

Фронт делаем поверх **настоящего** бэкенда и демо-базы из `../local-proj` (данные в ней синтетические).
Бэкенд — PHP-прокси: `MethodName` → хранимая процедура Firebird по таблицам `API_METHODS` и `API_METHOD_PARAMS`.
Вся логика, меню, колонки таблиц, кнопки и поля редакторов живут в базе.

**Запуск**

```bash
cd ../local-proj && docker compose up -d firebird api   # база :3050, API :8080
cd ../elevn_demo_crm && pnpm dev                        # /api.php проксируется на :8080
# логин DemoOpatra / 123456789
```

Без Docker — `pnpm dev:mocks` (MSW). Unit-тесты и e2e всегда идут на моках.

**Правила**

1. **Бэкенд и базу не меняем.** Ни PHP, ни процедуры, ни таблицы, ни данные меню. Не хватает метода
   или поля — не обходим на фронте, а записываем в [backend-requests.md](backend-requests.md).
2. **Контракт берём из базы, а не придумываем.** `pnpm api:describe <Метод>` показывает процедуру, описание,
   входные и выходные параметры. Имена параметров передаём как там (регистр не важен), ответ описываем
   zod-схемой по выходным параметрам. Типы из старого фронта (`src/api/**`) — подсказка, но база главнее.
3. **Все значения уходят строками.** Пустая строка, `null`, `false` бэкенд превращает в `NULL`, `"0"` — в 0.
   Булевы флаги отправляй как `1` / `0`.
4. **Ошибки бывают двух видов.** Конверт `result != 0` или `RESULT != 0` внутри первой строки при `result: 0`
   (так, например, отвечает логин). `callApi` проверяет оба. На неизвестный метод PHP просто рвёт соединение —
   это `ApiError` с `kind: 'network'`.
5. **Разделы не хардкодим.** Меню приходит из `WAGetNav`, маршрут считается из типа пункта
   (`features/navigation/model/item-types.ts`). Под раздел типа table/chart/dashboard не пишем отдельный
   экран — расширяем движок. Новый тип пункта → `item-types.ts` + `pnpm metadata:sync`.
6. **Моки — снимки реальности.** Метаданные (меню, колонки, кнопки, поля) снимаем с локального бэкенда
   скриптами (`pnpm metadata:sync`) и коммитим как фикстуры. Строки данных в фикстуры не кладём —
   генерируем faker-ом по типам колонок: так фикстуры маленькие и стабильные.
7. **Реестр разделов** — [sections.md](sections.md). Статус ✅ ставим только после проверки раздела
   на локальном бэкенде. После изменений меню в базе — `pnpm metadata:sync` и коммит реестра.
8. **Безопасность.** Бэкенд уязвим к SQL-инъекциям (параметры вклеиваются в SQL строкой), ходит в базу
   под SYSDBA и пишет в логи пароли. Фронт этого не закрывает и закрыть не может. Поэтому:
   - не подключаем новый фронт к публичному или боевому бэкенду, пока владелец бэкенда это не исправит;
   - не открываем локальный бэкенд в общую сеть (compose слушает 0.0.0.0:8080 и :3050 — работай
     в доверенной сети или закрой порты файрволом);
   - замена `'` → `` ` `` в `callApi` (`toBackendSafe`) — для совместимости, **не защита**;
   - не выводим в консоль тела запросов, пароли и `SessionUUID`.
9. **Никаких внешних ресурсов из базы.** В метаданных есть ссылки на старый домен (иконки меню) —
   не грузим их, маппим на свои иконки.

## Компоненты

- Сначала смотри `shared/ui` и `/dev/kit` — там все готовые компоненты.
- Нужен компонент, который пригодится обоим трекам? Сначала сделай его внутри своей фичи,
  перенеси в `shared/ui` отдельным PR, когда он понадобится второму.
- Компоненты shadcn: `pnpm dlx shadcn@latest add <name>` (конфиг — `components.json`). После генерации:
  - замени `bg-accent`/`text-accent-foreground` (у shadcn это hover-фон) на `bg-canvas-sunken` —
    у нас `accent` = брендовый синий только для действий;
  - откати правки CLI в `src/shared/styles/index.css`, если он их сделал;
  - добавь компонент в `shared/ui/index.ts` и на `/dev/kit`.
- Стили — только токены: `text-ink-muted`, `bg-canvas`, `rounded-md`, `shadow-hover`, `text-caption`…
  Стандартной палитры Tailwind (`bg-blue-500`) нет намеренно. Нужен новый токен — сначала
  `docs/design-system.md`, потом `src/shared/styles/tokens.css`, одним PR.
- Цвета статусов записи — только через `STATUS_STYLES` / `<StatusBadge>`.

## Формы

react-hook-form + zod. Поля из `shared/ui`: `TextField`, `NumberField`, `PhoneField`, `DateField`,
`SelectField`, `TextareaField`, `CheckboxField` — они сами связывают label, ошибку и aria-атрибуты.
Сообщения в zod-схеме — ключи из `common` (`'errors.required'`) или готовый текст.

## Переводы

- Общие строки — `src/shared/i18n/locales/*.json` (неймспейс `common`).
- Строки фичи — `features/<name>/locales/*.json`, в компоненте `useTranslation(NS)`.
- Ключи типизированы по `ru.json`: опечатка в `t('...')` — ошибка компиляции.
  Новый неймспейс? Добавь его в `src/app/i18next.d.ts`.

## Git

- Ветки: `a/<задача>`, `b/<задача>`, `shared/<задача>`; живут 2–3 дня.
- Conventional Commits: `feat(logbook): …`, `fix(handbook): …`.
- PR → зелёный CI + апрув второго → squash merge.
- Новая зависимость — отдельным PR с обоснованием. `pnpm add` пишет точную версию,
  свежие (< 3 дней) версии pnpm не поставит — это защита от захваченных пакетов.
