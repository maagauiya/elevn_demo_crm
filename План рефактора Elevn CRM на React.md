# План рефактора Elevn CRM на React

Nov 8, 2026 · @Aldiyar

Переписываем старый фронтенд (CRA, React 17, \~92 тыс. строк, antd 4 + MUI v4 + Redux) на Vite, React 19, Tailwind v4 и shadcn/ui по `design-system.md`. Разрабатываем поверх локального бэкенда и демо-базы с синтетическими данными: меню, таблицы, кнопки и формы задаются данными в базе. Разделов около 200, но рисуют их 8 движков, поэтому работу делим по движкам, а не по экранам. Бэкенд и базу не меняем.

## Как устроен бэкенд

Бэкенд — это PHP-прокси без бизнес-логики. На каждый запрос он находит по `MethodName` хранимую процедуру Firebird в таблицах `API_METHODS` и `API_METHOD_PARAMS`, подставляет параметры из запроса и возвращает строки. Вся логика — в базе: 2874 процедуры, 431 таблица, 1484 API-метода (1253 из них — Web).

Меню тоже хранится в базе (`WANAV`, `WAPANE`, `WAITEM`) и зависит от роли. Тип пункта меню определяет, какой движок его рисует. У администратора демо-базы 196 пунктов:

| Движок                                                            | Типы пунктов      | Пунктов | Маршрут              | Трек |
| ----------------------------------------------------------------- | ----------------- | ------- | -------------------- | ---- |
| Универсальная таблица: колонки, фильтры, кнопки, редактор из базы | 1, 7, 9, 10       | 178     | `/info/:itemId`      | B    |
| Дашборд из виджетов                                               | 6                 | 9       | `/dashboard/:itemId` | A    |
| График или виджет                                                 | 2, 3, 4, 5, 8, 11 | 4       | `/chart/:itemId`     | A    |
| Журнал записей                                                    | -1, -3            | 1       | `/logbook`           | A    |
| Расписание по кабинетам                                           | -10               | 1       | `/offices`           | A    |
| Групповые занятия                                                 | -100              | 1       | `/training`          | A    |
| График работы                                                     | -2                | 1       | `/work_schedule`     | A    |
| Канбан (в старом фронте не было)                                  | 12                | 1       | `/kanban/:itemId`    | B    |

Полный список со статусами — `docs/sections.md` в репозитории. Его генерирует `pnpm metadata:sync` из меню локального бэкенда.

## Структура репозитория

Репозиторий режется по фичам: каждая фича — отдельная папка со своим API, моками, переводами и роутами. Благодаря этому два человека практически не трогают одни и те же файлы.

```
/
├─ mockups/              # dashboard.html, logbook.html — визуальный эталон
├─ docs/                 # design-system.md, PLAN.md, ADR
├─ public/
├─ src/
│  ├─ app/               # точка входа, провайдеры, router, AppShell (меню, шапка)
│  ├─ shared/            # общее, меняется только через ревью второго
│  │  ├─ ui/             # shadcn-компоненты + продуктовые примитивы
│  │  ├─ styles/         # tokens.css (@theme из design-system.md)
│  │  ├─ api/            # callApi(), очередь/ретраи, типы ответа, ошибки
│  │  ├─ mocks/          # MSW worker + реестр хендлеров по MethodName
│  │  ├─ i18n/           # инициализация, общий неймспейс common
│  │  ├─ hooks/          # useDebounce, useMediaQuery и т.п.
│  │  └─ lib/            # даты, телефон, форматтеры, cn()
│  └─ features/
│     ├─ auth/           # фаза 0
│     ├─ logbook/        # трек A
│     ├─ dashboard/      # трек A
│     ├─ work-schedule/  # трек A
│     ├─ notifications/  # трек A
│     ├─ navigation/     # оба: меню из WAGetNav, тип пункта → движок
│     ├─ handbook/       # трек B: движок таблиц /info/:itemId
│     ├─ kanban/         # трек B: канбан /kanban/:itemId
│     ├─ multiselect/    # трек B
│     ├─ dental/         # трек B (зубная формула, карта зубов)
│     └─ billing/        # трек B (лицензии, оплата, касса)
└─ e2e/                  # Playwright
```

Внутри каждой фичи одинаковая раскладка: `api/` (типы + zod-схемы + query-хуки), `mocks/` (фикстуры и MSW-хендлеры), `components/`, `routes.tsx`, `locales/ru.json` и `locales/en.json`, `index.ts` (публичный API фичи).

Правила границ (проверяются ESLint-правилом `no-restricted-imports`):

1. `features/*` может импортировать `shared/*` и только `index.ts` другой фичи, никогда её внутренние файлы.
2. `shared/*` не импортирует ничего из `features/*` и `app/*`.
3. Роуты фичи подключаются в `app/router.tsx` одной строкой через lazy-импорт. В фазе 0 все строки уже есть, так что конфликтов в этом файле не будет.
4. Мок-хендлеры фича регистрирует сама в своём `mocks/index.ts`. Общий реестр их только собирает.
5. Переводы — в неймспейсе своей фичи, а не в одном общем `ru.json` (сейчас это главный источник merge-конфликтов).

## Правила работы с локальным бэкендом

Источник истины — локальный бэкенд и демо-база из `local-proj`. Запуск: `docker compose up -d firebird api`, затем `pnpm dev`, логин `DemoOpatra` / `123456789`.

1. **Бэкенд и базу не меняем.** Ни PHP, ни процедуры, ни таблицы, ни данные меню. Не хватает метода или поля — не обходим на фронте, а записываем в `docs/backend-requests.md`.
2. **Контракт — из базы.** `pnpm api:describe <Метод>` показывает входные и выходные параметры. Типы из старого фронта — подсказка, база главнее.
3. **Все значения — строки.** Пустая строка, `null` и `false` бэкенд превращает в NULL. Булевы флаги отправляем как `1` / `0`.
4. **Разделы не хардкодим.** Меню — из `WAGetNav`, маршрут — из типа пункта. Под раздел типа table, chart или dashboard не пишем отдельный экран — расширяем движок.
5. **Моки — снимки реальности.** Метаданные (меню, колонки, кнопки, поля) снимаем скриптами с локального бэкенда в фикстуры. Строки данных генерируем faker-ом по типам колонок. Unit-тесты и e2e в CI идут на моках.
6. **Раздел готов, когда проверен на локальном бэкенде.** Только тогда ставим ✅ в реестре `docs/sections.md`.
7. **Не подключаем новый фронт к боевому бэкенду**, пока владелец не закроет SQL-инъекцию (см. «Безопасность»). Локальный бэкенд не открываем в общую сеть.
8. **Никаких внешних ресурсов из базы.** Иконки меню ссылаются на старый домен — не грузим их, маппим на свои.
9. **Меню зависит от роли.** Проверяем разделы не только под администратором: скрытые пункты и права `ISEDITABLE` приходят с сервера.

## Точки стыка

Треки пересекаются в четырёх местах. В каждом заранее договариваемся о контракте (типы + сигнатура хука/компонента). Пока реализации нет, тот, кто её ждёт, работает с заглушкой.

| Что                                                                 | Владелец          | Потребитель                | Как не ждать                                                                                                                     |
| ------------------------------------------------------------------- | ----------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Генератор серверных кнопок (кнопки карточки записи `AppButtonList`) | B (`handbook`)    | A (`logbook`)              | В начале фазы 2 B кладёт в `handbook/index.ts` контракт `<ServerActionButtons … />`. До того A показывает кнопки простым списком |
| Таблица внутри дашборда и карточки клиента (отчёт как виджет)       | B (`handbook`)    | A (`dashboard`, `logbook`) | B экспортирует `<MetaTable itemId params />`. До того A ставит заглушку с тем же API                                             |
| Кассовые методы для формы оплаты в журнале                          | B (`billing`)     | A (`logbook`)              | B кладёт в `billing/index.ts` типы и хук `useCreateCheck()` с моком, реализация позже                                            |
| Выбор клиента/услуги в формах журнала                               | B (`multiselect`) | A (`logbook`)              | В фазе 1 — простой Combobox, потом один импорт `<DictionaryPicker>`                                                              |
| Навигация, типы пунктов, `metadata:sync`, `callApi`, UI-кит         | оба               | оба                        | Маленькие отдельные PR с ревью второго. Новый снимок метаданных — отдельным коммитом                                             |

Правила, чтобы не блокировать друг друга:

- Нужен новый общий компонент — сначала делаешь его внутри своей фичи. В `shared/ui` переносишь отдельным PR, когда он понадобился второму.
- Новый токен или паттерн — сначала правка в `docs/design-system.md`, потом в `tokens.css`, одним PR.
- Никакого глобального стора. У каждой фичи свои query-ключи и свой Zustand-стор (если нужен). Инвалидация чужих данных — только через экспортированный из `index.ts` хелпер.
- Раз в неделю — 15 минут синка: что появилось в `shared/`, какие контракты нужны на следующей неделе.

## Git-процесс и Definition of Done

`main` защищён: в него попадают только PR с зелёным CI и аппрувом второго. Сливаем через squash.

- Ветки: `a/logbook-grid`, `b/handbook-table`, `shared/date-field`. Ветка живёт не дольше 2–3 дней, большие задачи режем.
- Коммиты в формате Conventional Commits: `feat(logbook): …`, `fix(handbook): …`.
- `CODEOWNERS`: `features/logbook|dashboard|work-schedule|notifications` → A, `features/handbook|multiselect|dental|billing` → B, `shared/`, `app/`, `docs/` → оба.
- Каждое утро — `git pull --rebase origin main`. Изза раскладки по папкам конфликты бывают только в `shared/` и lock-файле.
- Новая зависимость — отдельным PR с одной строкой обоснования, чтобы не драться за `pnpm-lock.yaml`.

Экран считается готовым, когда:

1. Визуально соответствует `design-system.md` (и мокапу, если он есть). В коде нет сырых hex-цветов и чисел вне шкалы.
2. Работает на локальном бэкенде (раздел отмечен ✅ в реестре) и на моках во всех состояниях: загрузка (Skeleton), пусто (EmptyState), ошибка, данные.
3. Все тексты в i18n, ru и en.
4. Работает с клавиатуры, есть видимый focus-ring, статус не кодируется только цветом.
5. Есть тесты на логику (хуки, утилиты, расчёт сетки) и один тест рендера на основной сценарий. Для ключевых экранов — e2e в Playwright.
6. Нет `any` и `// eslint-disable` без комментария, зачем они нужны.

## Безопасность

Уязвимости старого фронта берутся из трёх источников: устаревший webpack 4 и CRA, десятки билд-инструментов в `dependencies` и секреты прямо в коде. В новом проекте закрываем все три.

**Зависимости**

- Минимум пакетов; каждая новая зависимость — отдельный PR с обоснованием. Билд-инструменты только в `devDependencies`.
- Точные версии и закоммиченный `pnpm-lock.yaml`. В CI — `--frozen-lockfile`.
- В `pnpm-workspace.yaml` включаем `minimumReleaseAge` (например, 3 дня): свежеопубликованные версии не ставятся. Это защита от атак через взломанные npm-пакеты.
- postinstall-скрипты запрещены по умолчанию (поведение pnpm 10), разрешённые перечислены в `onlyBuiltDependencies`.
- Renovate раз в неделю собирает обновления в группы; security-обновления приходят сразу. `pnpm audit --prod` в CI падает на high/critical.
- Не переносим: `xlsx` из npm (известные уязвимости, в npm больше не обновляется), `moment`, `axios` 0.27, две UI-библиотеки, три варианта emoji-picker.

**Код**

- В старом `src/api/api.ts` захардкожены три API-ключа и адрес прокси. В новый проект их не копируем. Любая `VITE_*`-переменная попадает в бандл и публична, поэтому там только адреса, а секреты живут на бэкенде. `.env` — в `.gitignore`, в репозитории только `.env.example`.
- В моках только синтетические данные из faker, никаких выгрузок реальных пациентов.
- `dangerouslySetInnerHTML` запрещён линтером; если без HTML с сервера не обойтись — только через DOMPurify.
- Идентификатор сессии не храним в localStorage дольше нужного. Как именно хранить сессию, решаем вместе с бэкендом при подключении API (см. открытые вопросы).
- Для деплоя: CSP и заголовки безопасности в nginx, сорсмапы не публикуются.

**Бэкенд (вне рамок проекта, блокирует релиз)**

Бэкенд мы не меняем, но без этих исправлений выпускать новый фронт нельзя. Список для владельца — `docs/backend-requests.md`.

- SQL-инъекция во всех параметрах: PHP вклеивает значения в SQL строкой, в том числе `ApiKey` до авторизации. Замена `'` на `` ` `` на фронте — не защита.
- Подключение к базе под `SYSDBA` с паролем в коде.
- CORS отражает любой `Origin` вместе с credentials.
- В `logfiles` пишется весь вход, включая пароли.
- На неизвестный метод соединение обрывается без ответа.
