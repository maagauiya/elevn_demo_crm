# REFACTOR_PLAN.md

План полного редизайна фронтенда **haim-crm** (Sycret CRM) под дизайн-систему,
обкатанную в этом мокап-репозитории. Документ — рабочий чек-лист для команды
из 2 человек: этапы, технические решения, критерий «готово» для экрана и
git-процесс. Обновляется по ходу работы (отмечаем чекбоксы, уточняем владельцев).

Источник истины по визуалу — [`design-system.md`](./design-system.md). Если
во время рефактора экрана не хватает токена/паттерна — сначала дополняем
`design-system.md`, потом код (см. `AGENT.md`).

## Цель и границы

- **Цель:** все экраны реального приложения haim-crm визуально однообразны и
  соответствуют `design-system.md` — те же цвета статусов, spacing, elevation,
  типографика, что уже реализованы в `dashboard.html` и `logbook.html`.
- **Не цель этого документа:** менять бизнес-логику, API, схему БД. Рефактор —
  только слой представления (компоненты, стили, разметка).
- Этот план и сопутствующие обсуждения живут в мокап-репозитории. Сам рефактор
  кода выполняется в репозитории **haim-crm** (основной монорепозиторий) —
  мокап-репо сюда не трогаем при переносе.

## Статус-кво

| Что | Состояние |
|---|---|
| Дизайн-система | Готова (`design-system.md`) |
| Эталонные экраны-мокапы | `dashboard.html`, `logbook.html` — референс для «как должно выглядеть» |
| Реальный React-фронтенд | Экраны инвентаризированы (см. [«Реестр экранов»](#реестр-экранов)); CSS-подход в коде смешанный, целевой подход выбран в [задаче 1.2](#задача-12--выбор-единого-подхода) |
| Команда | 2 человека, срок не зафиксирован — идём по этапам, а не по датам |

## Этап 1 — Аудит CSS-подхода и инфраструктура токенов

Текущий React-код стилизован без единого подхода. Прежде чем рефакторить
экраны, нужно решить, как токены из `design-system.md` попадают в код —
иначе каждый экран будет решать это по-своему, и однообразия не получится.

### Задача 1.1 — Аудит текущих стилей
- [x] Пройтись по компонентам, зафиксировать, что реально используется:
      plain CSS, CSS Modules, styled-components, inline-стили, Tailwind,
      UI-кит (MUI/AntD/свой) — и в каком объёме каждый подход встречается.
- [x] Короткий вывод (3-5 строк) в раздел ниже: можно ли мигрировать
      постепенно на единый подход, или легаси придётся обходить точечно.

**Результат аудита** (полная версия — [`ANALYSIS_RESULTS.md`](./ANALYSIS_RESULTS.md)):
доминирует MUI v4 `makeStyles`/JSS (226 файлов, 303 импорта `@material-ui/*`),
вторым слоем — antd 4.18 (37 файлов, в основном `Menu` и формы), плюс точечные
inline-стили (84 файла) как оверрайды поверх JSS. CSS Modules почти не
используются (1 файл), `styled-components` и Tailwind — отсутствуют вовсе.
Переписать всё разом нереалистично (226 файлов на `makeStyles`) — миграция
должна идти постепенно, экран за экраном, вместе с рефактором под новую
дизайн-систему, а не отдельным шагом до него.

### Задача 1.2 — Выбор единого подхода
Рекомендация по умолчанию, если команда не хочет тратить время на отдельное
решение: **CSS-переменные в корневом файле + CSS Modules на компонент** —
это прямой перенос токенов из `design-system.md` (они уже оформлены как
HEX/px таблицы) без завязки на дополнительный build-инструмент сверх того,
что уже есть в CRA/Vite. Если в коде уже превалирует Tailwind или
styled-components — выгоднее остаться на нём и завести токены туда же, лишний
масштабный conversion того не стоит.

- [x] Зафиксировать выбор (и причину) здесь:
      **Подход:** MUI (`makeStyles`/JSS, с перспективой перехода на
      `@mui/material` v5+ `styled`/`sx`) — остаёмся на том, что уже
      доминирует в коде (226 файлов), вместо навязывания CSS Modules поверх
      легаси. Токены `design-system.md` переносим в MUI `theme` (`theme.palette`,
      `theme.shadows`, `theme.spacing`) — это даёт тот же единый источник
      токенов без масштабной конвертации. antd (37 файлов) и разрозненные
      inline-стили (84 файла) выпиливаем точечно по мере рефактора каждого
      экрана, начиная с P0 (Logbook, Dashboard, навбар) — отдельного этапа
      миграции на них не выделяем.
- [ ] Завести единый источник токенов в коде (файл переменных / tailwind
      config / theme-объект) — 1:1 переносим таблицы цветов, типографики,
      spacing, радиусов, elevation из `design-system.md`.
- [ ] Вынести повторяющиеся примитивы в общие компоненты, которые дальше
      используются на всех экранах (не копипастить per-screen):
  - Статус-бейдж (цвет = сигнал, зачёркивание для «отменено»)
  - Карточка/панель (hairline в покое, тень только на hover/drag)
  - Primary/secondary кнопка, icon-button
  - Filter-chip, сегмент-контрол (pill)
  - Таблица/список с плотной строкой

**Владелец:** один человек ведёт эту задачу целиком (инфраструктура должна
быть сделана один раз и согласованно, не параллельно двумя людьми).

## Tech spec — критерий «готово» для экрана

Экран считается отрефакторенным, если проходит весь чек-лист (сверяем
визуально в браузере, не только по коду — см. `AGENT.md`):

- [ ] Все цвета берутся из токенов `design-system.md`, нет хардкод-HEX в коде.
- [ ] Статус (если есть) закрашен тоном + полоса слева, а не только текстом/иконкой.
- [ ] Отменённые/неактивные состояния дублируют сигнал не только цветом
      (зачёркивание, иконка) — для дальтоников и ч/б печати.
- [ ] Accent-синий используется только для действий (кнопки/ссылки/выбор),
      не для статусов записи.
- [ ] Тень есть только на интерактивных/поднятых элементах (hover, drag,
      popover, FAB) — в покое всё плоское (hairline-граница).
- [ ] Spacing — по шкале 4/8/12/16/20/24/32, не произвольные значения.
- [ ] Типографика — по шкале токенов (title/subtitle/label/body/caption/micro),
      не произвольные size/weight.
- [ ] Радиусы — по токенам (xs/sm/md/lg/pill) согласно типу элемента.
- [ ] Плотность: компакт-режим по умолчанию, не растянуто ради «воздуха».
- [ ] Общие примитивы (бейдж, карточка, кнопка, чип) взяты из общих
      компонентов (Этап 1.2), а не продублированы на экране.
- [ ] Экран визуально сверен в браузере бок-к-бок с `dashboard.html` /
      `logbook.html` — ощущается как часть той же системы.

## Git-процесс

- **Одна задача = одна ветка** от актуального main/develop основного репозитория:
  - Инфраструктурные задачи: `refactor/design-tokens-setup`,
    `refactor/shared-components`.
  - Рефактор экрана: `redesign/<screen-slug>` (например `redesign/patients-list`).
- **PR маленький и по теме** — один экран/один примитив на PR, не «рефактор всего разом».
- **Ревью — взаимное** (команда из 2 человек): автор PR не мержит свой же PR без
  ревью второго участника.
- **Условие мержа:** чек-лист из [Tech spec](#tech-spec--критерий-готово-для-экрана)
  пройден и явно отмечен в описании PR (скриншот до/после — обязателен).
- Порядок: сначала мержится Этап 1 (инфраструктура токенов и общие компоненты),
  потом экраны Этапа 2 ссылаются на неё — не наоборот, иначе каждый экран
  тащит свой временный вариант токенов.

## Этап 3 — Финальный аудит однообразия

Когда все экраны из реестра отмечены ✅:

- [ ] Пройтись по всему приложению подряд (не по одному экрану, а именно
      переключаясь между ними) и проверить, что ощущение единой системы не
      ломается на стыках (переходы между экранами, общие элементы навигации).
- [ ] Сверить, что нет больше двух параллельных реализаций одного и того же
      примитива (бейдж/карточка/кнопка) — к этому моменту всё должно идти
      через общие компоненты из Этапа 1.
- [ ] Вычистить мёртвый CSS/компоненты старого стиля, оставшиеся от старых
      экранов.
- [ ] Обновить `design-system.md`, если в процессе рефактора появились новые
      легитимные паттерны, которых не было на старте.

## Примечания

- Это мокап-репозиторий (`CLAUDE.md`) — физический рефактор кода происходит в
  основном репозитории haim-crm, а не здесь. Здесь — только план и
  дизайн-система как источник истины.
- Не трогаем `backend/`, `db/`, `deploy/` и бизнес-логику — рефактор строго
  про слой представления.
- Любые новые визуальные паттерны, которых не хватает в `design-system.md`,
  сначала предлагаются и добавляются туда, а не заводятся инлайн в компоненте.
